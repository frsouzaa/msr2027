\begin{abstract}
    Frameworks and libraries are essential in software development, providing common functionality for projects and speeding up the development process.
    When starting new projects that involve software reuse, it is important to choose libraries and frameworks that can be maintained over the long term, thereby avoiding rework and changes that would incur additional costs for the maintenance of the software projects.
    This study aims to understand which features present in code repositories and software ecosystems--such as commits, forks, and relative interest--can indicate the lifecycle stage of libraries and frameworks, thus pointing out those suitable for use in software projects.
    So far, we have collected data from 30 real-world open-source projects, covering 10 programming languages, and analyzed the correlation between repository features. We also examined how these features change over time using the Exponential Moving Average, which serves as a trend indicator for prices in economics.
    The preliminary results indicate that some features, such as created pull requests, created issues, and commits, are highly correlated with their respective authors. We also plotted these features over the lifespan of the project, which makes it possible to observe variations--for instance, in the number of stars and the level of interest in the projects evaluated thus far.
    The next steps will involve choosing other features--such as the dependencies between projects--selecting the features that best distinguish the lifecycle stage of frameworks and libraries, and employing time-series prediction algorithms such as AutoRegressive Integrated Moving Average (ARIMA).
\end{abstract}

\section{Introduction}
Developing software systems is a complex and essential activity present in most economic domains and human relationships. Software reuse is an efficient strategy to speed up the software development lifecycle and to implement common functionalities provided by frameworks and libraries.
Frameworks are code structures for all or part of a system that must be implemented when building software systems \cite{johnson1997}. Some examples are testing and web frameworks. A software library contains code functions from a specific domain ready for reuse in other software projects. Some examples are libraries for parsing file formats or finding text patterns. Libraries can be called directly in code, while frameworks invert control, calling their own sequences of activities \cite{johnson1988}.

However, software reuse also presents certain disadvantages stemming from a dependency on libraries and frameworks. Keeping these third-party dependencies up to date can be challenging. Some may become outdated due to a lack of maintenance and could contain bugs or vulnerabilities that make them unsuitable for continued use over time. Furthermore, new libraries and frameworks may emerge that perform better or benefit from a more active community.

When designing a software system, it is important to choose frameworks and libraries that can be maintained over time, thereby avoiding rework and unnecessary changes. Even well-established frameworks and libraries can become obsolete due to issues such as a lack of documentation  \cite{robillard2011,zhong2013}, difficulty of use \cite{nadi2016}, or incompatibility due to API changes \cite{mostafa2017,decan2019}.

As with other software systems, frameworks and libraries go through various stages of evolution: initial development, maintenance, improvement, and eventually, decline. Therefore, it is important to consider their relevance and robustness over time. Well-established software tools typically have an active community of developers, which may indicate their long-term sustainability. Also, the support for usage and source code updates may indicate their current lifecycle stage.

Mining software repositories (MSR) can be used to analyze the evolution patterns of open source software projects over time \cite{gold2022,hassan2008}. Therefore, applying MSR to frameworks and libraries may be helpful to analyze how software projects use such tools and how the features present in their repositories (e.g., issues, commits, stars, bug reports, etc.) evolve.

In this study, we are developing a methodology to predict the lifecycle stage of frameworks and libraries. To do this, we use data from repositories of open source libraries and frameworks, as well as other data sources, such as build and dependency management tools (e.g., npm, Maven), Q \& A websites, and code quality metrics. Our goal is to provide a decision-support tool that can be useful for software teams to decide which libraries and frameworks should be chosen to include in software development projects.

In our preliminary analyses presented in this work, we analyze the correlation of 15 repository features related to source code evolution and projects' popularity. We also present how these features evolve over the projects' timeline using the Exponential Moving Average (EMA), a time series trend indicator used in economics \cite{hunter1986}. We selected a sample of 30 repositories, including real-world frameworks and libraries from 10 programming languages. These data will be used to select features for the model we are building. We will evaluate those features using Machine Learning models--such as random forest--and time series forecasting statistical models such as AutoRegressive Integrated Moving Average (ARIMA) and its variants (e.g., SARIMA, SARIMAX) to respond to the following research questions.

\subsection{Research Questions}

\begin{itemize}
    \item \textbf{RQ1} How accurate is the proposed method in predicting the lifecycle stage of libraries and frameworks?
    \item \textbf{RQ2} What are the most relevant code repository features to predict lifecycle stage?
    \item \textbf{RQ3} How early can our method determine whether a project is in a downtrend or uptrend?
\end{itemize}

\section{Related Work}
\label{sec:background}
Previous studies have investigated how repository features can help to understand software evolution. This section presents the state of the art and how our work may expand it.

The K-Spectral Centroid (KSC) algorithm used features such as stars, contributors, forks, commits, and project age \cite{borges2016}. Based on the resulting clustering model, the authors proposed the following patterns of repository popularity growth: slow, moderate, fast, and viral. Also, the study pointed out a strong correlation between stars and forks.

% The correlation of popularity metrics such as stars and forks has been studied in \cite{wang2023}; the same study also discusses the correlation inside README.md file attributes--number of lines, number of images, update interval, etc.--and how it is related to the popularity of the repository. One of the study conclusions is that the repository popularity is directly correlated with the frequency and number of updates in README.md files.

The study of \cite{coelho2020} built a Random Forest model based on repository features--such as commits, developers, issues, pull requests, etc. The proposed model was able to predict whether a repository is maintained or not. Furthermore, the authors established a metric to assess the risk of projects becoming unmaintained. A browser extension tool, which is no longer available, was designed to extract data and calculate the proposed metrics for new repositories. Additionally, the correlation analysis presented serves as an interesting example of how correlation helps identify which data should be discarded during the training of predictive models.

Package centrality is the method proposed by \cite{mujahid2022} for identifying packages in decline. This methodology involves applying Google's PageRank algorithm to the dependency relationships between npm packages. By performing this procedure based on historical records, the authors were able to predict whether or not a project is in decline. The authors developed a Chrome browser extension that displays this centrality, along with other metrics, on the npm website.

% Alongside other 92 factors, \cite{zhang2023} studied how developers and integrators relate to each other, and how these relations can influence the acceptance rate of pull requests.

Although limited in scope, the lifecycle analysis conducted by \cite{soupinski2022} identified that prior to the repository's official death, there is a tendency toward low response rates on Stack Overflow and issue resolution. Following the death, there is no further evolution in the number of codebase commits.

\subsection{Research Scope and Contributions}
In addition to using features presented in previous studies, this research analyzes Google Trends' relative interest, as well as the authors and reviewers of issues and pull requests. In the next phase, we will include other features such as watchers, releases, question-and-answer (Q\&A) website content, dependency managers' usage information (e.g., npm, Maven), source code quality metrics, and bug reports. We intend to apply various predictive models to the collected data, including machine learning models (e.g., Random Forest, SVM) and statistical time-series forecasting models (e.g., ARIMA, SARIMAX). However, to do this, a fundamental step is to examine the correlation between features to select them and conduct an initial trend analysis, which is the focus of this paper.

\section{Methodology}
\label{sec:methodology}
This section presents our methodology, which includes the steps done until now--the process of data gathering, preparation, and analysis--, according to the best practices for MSR \cite{cookbook}. Also, we describe the next steps we planned for this research.

\subsection{Data Gathering and Preparation}
\label{gathering}
Prior to the gathering phase, we first needed to define a systematic and reproducible method for selecting which GitHub repositories would be the subject of our work.

We used the SEART GitHub search tool \cite{seart} to find the repositories that best fit our purposes. The following filters were applied: non-fork repositories created before 1\textsuperscript{st} January 2021, with active issues and pull request functionality, containing at least 1,000 commits, 500 issues, 500 pull requests, 500 stars, 100 forks, and 1 release. These criteria resulted in a sample of 6,448 repositories. Then we ranked the top 10 languages--based on the primary language of the projects in the sample--which were: Python (16.10\% of the repositories), TypeScript (13.62\%), Go (10.72\%), C++ (10.02\%), JavaScript (9.65\%), Java (8.82\%), C\# (5.20\%), C (4.93\%), PHP (4.39\%), and Rust (4.03\%). As our objective for this work was to analyze popular and well-established projects, the repositories were ordered by the number of stars, and the top 15 repositories of each language were selected. To perform the final selection, we analyzed all 150 resulting repositories and picked 3 library or framework projects of each language. The selected repositories can be found in Table \ref{table:repositories}.

With our 30 projects in hand, the next step was to collect the history for each one of the 15 repository features. To achieve this, we rely on the use of PyDriller \cite{pydriller}, PoolinGH \cite{poolingh}, and pytrends-modern\footnote{https://github.com/yiromo/pytrends-modern}.

PyDriller is a library used to collect data available within Git itself and does not require communication with the GitHub API. It was used to collect commits and commit authors.

PoolinGH is a JavaScript library used to collect data that requires communication with the GitHub API. To make better use of the rate-limit consumption, we made use of both REST and GraphQL APIs. This library, in particular, was very useful to queue the thousands of requests we had to make and handle the errors returned by GitHub APIs. We used PoolinGH to collect forks, created issues, closed issues, authors that created issues, authors that closed issues, created pull requests, closed pull requests, merged pull requests, authors that created pull requests, authors that closed pull requests, authors that merged pull requests, and stars.

Pytrends-modern is a Python library used to collect Google Trends popularity data. This tool is a successor to the archived pytrends\footnote{https://github.com/GeneralMills/pytrends} library. This library was used to collect the Google relative interest of the repositories.

With the historical data collected for each repository, a crucial step before proceeding with the analysis is the normalization of the dataset. \subsection{Analysis}
\label{analysis}
Our initial analysis is composed of statistical correlation analysis and calculation of the Exponential Moving Average (EMA) over the chosen features.
Before calculating the correlation between collected features, we performed an Anderson-Darling (AD) test \cite{anderson.darling} for each feature in each repository. AD test is used to determine whether a dataset follows a specific distribution. In our case, we employed it to verify whether the data follows a normal distribution. We consider the distribution to be normal when the p-value is greater than 0.05. Otherwise, the feature does not follow a normal distribution.

With this information, we applied Pearson's and Spearman's correlations to the data. Both methods range between -1 and 1. For the pairs of features in which both have a normal distribution, we applied Pearson's correlation, as it is more appropriate for this use case \cite{pearson.spearman}. Otherwise, Spearman's rank correlation was applied in the analysis. For both Pearson and Spearman, we consider values above 0.7 to be a high correlation, and values below 0.3 to be a low correlation. Otherwise, the value has a moderate correlation.

We also applied EMA to all the collected features. The EMA is used to generate averages that are more sensitive to recent data points than to older ones. This is well-suited to our scenario, in which new events--such as commits, issues, stars, etc.--are more relevant than past events when assessing the current stage of a repository's lifecycle. For this study, we considered two distinct values for the EMA weighting factor ($\alpha$): $\alpha$ = 0.16 (short-term EMA), to produce a metric more sensitive to recent data, and $\alpha$ = 0.08 (long-term EMA), for a metric less sensitive to new changes. By comparing the two, we can determine whether a project shows a downward trend, an upward trend, or is stable. If the short-term EMA value is higher than the long-term EMA value, the feature is considered to be in an upward trend. Otherwise, it is in a downward trend. If the values are equal, the feature is considered stable.

\section{Preliminary Results}
\label{sec:results}
From these initial experiments, we recorded 59,554 distinct pull request creators and 468,957 pull requests created. Of these pull requests, 273,062 were closed, and 183,546 were merged, with 12,349 pull requests still open at the time of writing this paper. Regarding issues, 390,554 issues were recorded, created by 156,105 distinct users. Of these, 353,274 were closed, leaving 37,280 issues open. In addition, we collected 886,458 commits authored by 38,917 distinct authors.

All 30 repositories we analyzed showed a high correlation between the number of pull requests created and the number of authors who created them. Vue was the project with the highest correlation between these features. Fig. \ref{vue} shows the history of these features for this repository. The same was true for the relationship between issues created and their respective creators, as well as between closed pull requests and the individuals who closed them --a high correlation was observed in 29 repositories. Furthermore, 28 repositories showed a high correlation between closed issues and the individuals who closed them. Regarding commits and their authors, as well as merged pull requests and the individuals who performed those merges, we identified 27 repositories with a high correlation. It is worth noting that, in all these cases, the projects that did not exhibit a high correlation fell into a moderate range.

On the other side, features related to popularity--which in this study is represented by stars, forks, and Google relative interest--generally showed a low to moderate correlation when compared with features related to software development--commits, issues, pull requests, and their respective authors. Among these, forks and stars formed the pair with the highest number of instances classified as having a high correlation, spanning 13 repositories. The pairs (stars, relative interest) and (forks, relative interest) showed, respectively, 24 and 26 repositories with a low to moderate correlation. It is worth noting that the only pairs that did not show any repositories with a high correlation were (forks, commits) and (forks, commit authors), which may be related to the high correlation that exists between commits and the authors of those commits.

Figures \ref{react} and \ref{pytorch} illustrate the correlation plots for React and PyTorch, respectively. These two libraries differ in terms of correlation: while React largely follows the trends presented earlier, PyTorch represents an edge case, in which most features exhibit a moderate to high correlation with one another.

Based on the EMA analysis, we observe that commits, pull requests, forks, and interest show an upward trend in the majority of the analyzed repositories, while issues and stars show a downward trend in most of them. \section{Conclusion}
\label{sec:conclusion}
Features derived from issues, commits, and pull requests (e.g., created and closed issues) are highly correlated but distinct from the others (e.g., created issues and created pull requests). Using EMA, the resulting charts reveal trends, specifically whether there is an upward or downward trajectory. These trends will be used to determine the lifecycle stage of frameworks and libraries after we choose the most relevant features.

The next steps include using PCA (Principal Component Analysis) for feature selection. We will also include more projects using SEART. Then, we will use several time series analysis techniques to predict the lifecycle trends of frameworks and libraries.
