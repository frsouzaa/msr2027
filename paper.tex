\begin{abstract}
Frameworks and libraries are essential in software development, providing common functionality for projects and speeding up the development process. 
When starting new projects that involve software reuse, it is important to choose libraries and frameworks that can be maintained over the long term, thereby avoiding rework and changes that would incur additional costs for the maintenance of the software projects.
This study aims to understand which features present in code repositories and software ecosystems--such as commits, pull requests, and forks--can indicate the lifecycle stage of libraries and frameworks, thus pointing out those suitable for use in software projects.
In this first stage, we collected data from 30 real-world open-source projects across 10 different programming languages and analyzed the correlation between repository characteristics, such as commits, issues, and pull requests. We also examined the evolution of commits over time using the Exponential Moving Average.
The preliminary results indicate that some features such as created pull requests, created issues, and commits are highly correlated with their respective authors. We also plotted these features over the lifespan of the project, which makes it possible to observe variations—for instance, in the number of stars and the level of interest in the projects evaluated thus far.
The next steps will involve choosing other features--such as the interdependencies between projects--selecting the features that best distinguish the lifecycle stage of frameworks and libraries, and employing time-series prediction algorithms such as ARIMA (AutoRegressive Integrated Moving Average) and SARIMA (Seasonal ARIMA).
\end{abstract}

\section{Introduction}
Developing software systems is a complex and essential activity present in most economic domains and human relationships. Software reuse is an efficient strategy to speed up the software development lifecycle and to implement common functionalities provided by frameworks and libraries.
Frameworks are code structures for all or part of a system that must be implemented when building software systems \cite{johnson1997}. Some examples are testing and web frameworks. A software library contains code functions from a specific domain ready for reuse in other software projects. Some examples are libraries for parsing file formats or finding text patterns. Libraries can be called directly in code, while frameworks invert control, calling their own sequences of activities \cite{johnson1988}.

However, software reuse also presents certain disadvantages stemming from a dependency on libraries and frameworks. Keeping these third-party dependencies up to date can be challenging. Some may become outdated due to a lack of maintenance and could contain bugs or vulnerabilities that make them unsuitable for continued use over time. Furthermore, new libraries and frameworks may emerge that perform better or benefit from a more active community.

When designing a software system, it is important to choose frameworks and libraries that can be maintained over time, thereby avoiding rework and unnecessary changes. Even well-established frameworks and libraries can become obsolete due to issues such as a lack of documentation  \cite{robillard2011,zhong2013}, difficulty of use \cite{nadi2016}, or incompatibility resulting from API changes \cite{mostafa2017,decan2019}.

As with other software systems, frameworks and libraries go through various stages of evolution: initial development, maintenance, improvement, and eventually, decline. Therefore, it is important to consider their relevance and robustness over time. Well-established software tools typically have an active community of developers, which may indicate their long-term sustainability. Also, the support for usage and source code updates may indicate their current lifecycle stage.

\section{Literature Review}
Studies based on repository features can be very different from each other, specially when it comes to tools like GitHub, where a large number of functionalities can be found. In this section we will go through the state of the art and present how our work can complement it.

\subsection{Related Work}
Features like stars, contributors, forks, commits and project age have been studied in \cite{factors.impact.popularity}. It points that no correlation was found between stars and repository age, a weak correlation was noticed between stars, commits and contributors, and a strong correlation between stars and forks.

The correlation of popularity metrics such as stars and forks has been studied in \cite{readme.correlation}, the same study also discuss the correlation inside README.md file atributes--number of lines, number of images, update interval, etc.--and how it is related to the popularity of the repository. One of the study conclusions is that the repository popularity is directly correlated with the frequency and number of updates in README.md files.

The correlation analysis presented by \cite{random.tree} is an interesting example of how correlation is helpful in telling which data should be discarded when training prediction models. Among of other features analyzed, developers, issues and pull requests is a point in common with our work, the difference is that we look at the authors who performed the issues and pull requests actions, and not just at the events themselves.

Alongside with other 92 factors, \cite{pull.request.decisions} studied how developer and integrator relate to each other, and how this relations can influence on the acceptance rate of pull requests.

\subsection{Contributions}
Software repositories features--such as issues, pull requests, popularity, commits, among others--have already been extensively studied in different contexts. However, to the best of our knowledge, no study has yet been published that correlates issues and pull requests (as well as their respective authors and reviewers) with other repository popularity metrics.

\section{Methodology}
This section presents the process of data acquisition, preparation and synthesis, according to the best practices for Mine Software Repositories (MSR) proposed by \cite{cookbook}. The analysis process will be presented in the results section - \ref{results}.

\subsection{Data Acquisition and Preparation}
\label{acquisition}
Prior to the acquisition phase, we first needed to define a systematic and reproducible method for selecting which GitHub repositories would be the subject of our work.

We used the SEART GitHub search tool \cite{seart} to find the repositories that best fit our purposes. The following filters where applied: Non-fork repositories created before 1\textsuperscript{st} January 2021, with active issues and pull requests functionalities, containing at least 1,000 commits, 500 issues, 500 pull requests, 500 stars, 100 forks and 1 release. Resulting in a sample of 6,448 repositories. Then we ranked the top 10 main languages of the sample, which were: Python (16.10\% of the repositories), TypeScript (13.62\%), Go (10.72\%), C++ (10.02\%), JavaScript (9.65\%), Java (8.82\%), C\# (5.20\%), C (4.93\%), PHP (4.39\%) and Rust (4.03\%). As our objective for this work was to analyze popular and well-stablished projects, the repositories were ordered by the number of stars, and the top 15 repositories of each language were selected. To perform the final selection, we analyzed all the 150 resulting repositories and picked 3 library or framework projects of each language. The selected repositories can be found on table \ref{table:repositories}.

With our 30 projects in hand, the next step was to collect the history for each one of the repository features. To achieve this, we rely on the use of PyDriller \cite{pydriller}, PoolinGH \cite{poolingh} and pytrends-modern\footnote{https://github.com/yiromo/pytrends-modern}

PyDriller is a Python library used to collect data available within Git itself, and does not requires communication with the GitHub API. It was used to collect commits and commit authors.

PoolinGH is a JavaScript library used to collect data that requires communication with the GitHub API. To make better use of the rate-limit consumption, we made use from both Rest and GraphQL APIs. This library, in particular, was very useful to queue the thousands of requests we had to make and handle the errors returned by GitHub APIs. We used PoolinGH to collect forks, created issues, closed issues, authors that created issues, authors that closed issues, created pull requests, closed pull requests, merged pull requests, authors that created pull requests, authors that closed pull requests, authors that merged pull requests and stars.

Pytrends-modern is a Python library used to collect the Google Trends popularity data. This tool is a sucessor for the archived pytrends\footnote{https://github.com/GeneralMills/pytrends} library. This library was used to collect the Google relative interest of the repositories.

In addition to these tools, we also used the Python libraries Pandas\footnote{https://github.com/pandas-dev/pandas}, NumPy\footnote{https://github.com/numpy/numpy}, Matplotlib\footnote{https://github.com/matplotlib/matplotlib} and SciPy\footnote{https://github.com/scipy/scipy} to support the work presented in the sections \ref{synthesis} and \ref{results}.

It is worth noting that the inclusion of watchers would also be an interesting feature for this study, however, GitHub does not provide a way to collect the historical data regarding this feature. This means that it is only possible to obtain the number of watchers as it stands at the time of data collection, making our analysis impracticable for this feature.

With the historical data collected for each repository, a crucial step before proceeding with the analysis is the normalization of the dataset. First, we created a monthly view for each metric by aggregating authors and summing the events that were originally distributed on a daily basis. If a metric showed no recorded events for a given month, we assigned a value of zero for that month. Since all data were collected during the first week of October 2026, information pertaining to that month was excluded. Therefore, for each repository, we analyzed the period spanning from its creation up to September 2026. Subsequently, we consolidated all the various metrics into a unified view for each project to simplify further analysis.

\subsection{Synthesis}
\label{synthesis}
Before calculating the correlation of the data, we performed an Anderson-Darling (AD) test \cite{anderson.darling} for each feature in each repository. AD test is used to determine whether a dataset follows a specific distribution, in our case, we employed it to verify whether the data follows a normal distribution. We consider the distribution to be normal when the p-value is greater than 0.05, otherwise, we consider it non-normal.

With this information we applied Pearson's and Spearman's correlations to the data, both methods range between -1 and 1. For the pairs which both features represented normal distributions according to AD test, we considered Pearson's correlation, as it is more indicated for this use case \cite{pearson.spearman}. Otherwise, if none or only one of the features presents a normal distribution, Spearman's rank was considered in the final analysis. Finally, for both Pearson and Spearman, we consider values above 0.7 to be a high correlation, and values below 0.3 to be a low correlation. Any number falling within this range is considered a moderate correlation.

We also applied the Exponential Moving Average (EMA) method over all the collected features. The EMA is used to generate averages that are more sensitive to recent data points than to older ones, which fits well with our scenario, in which new events--whether they be commits, issues, stars, etc.--are more relevant than older ones when assessing the current stage of a repository's lifecycle. \section{Results}
\label{results}
At the end of the experiments, we recorded 59,554 distinct pull request creators and 468,957 pull requests created. Of these pull requests, 273,062 were closed and 183,546 were merged, with 12,349 pull requests remaining open at the time of writing this article. Regarding issues, 390,554 issues were recorded, created by 156,105 distinct users, of these, 353,274 were closed, leaving 37,280 issues open. In addition, we collected 886,458 commits authored by 38,917 distinct authors.

All 30 repositories we analyzed showed a high correlation between the number of pull requests created and the number of authors who created them, vue was the project with highest correlation between these features, Fig. \ref{vue} shows the history of these features for this repository. The same was true for the relationship between issues created and their respective creators, as well as between closed pull requests and the individuals who closed them - a high correlation was observed in 29 repositories. Furthermore, 28 repositories showed a high correlation between closed issues and the individuals who closed them. Regarding commits and their authors, as well as merged pull requests and the individuals who performed those merges, we identified 27 repositories with a high correlation. It is worth noting that, in all these cases, the projects that did not exhibit a high correlation fell into a moderate range.

On the other side, features related to popularity--which in this study is represented by stars, forks and Google relative interest--generally showed a low to moderate correlation when comparing with features related to software development--commits, issues, pull requests and their respective authors. Among these, forks and stars formed the pair with the highest number of instances classified as having a high correlation, spanning 13 repositories. The pairs (stars, relative interest) and (forks, relative interest) showed, respectively, 24 and 26 repositories with a low to moderate correlation. It is worth noting that the only pairs that did not show any repositories with a high correlation were (forks, commits) and (forks, commit authors), which may be related to the high correlation that exists between commits and the authors of those commits.
